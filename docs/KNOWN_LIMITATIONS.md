Measured, not promised. Hardware: Linux 7.0.0-43-generic, 4 CPUs,
7.9 GB RAM, Python 3.12.3 / SQLite 3.45.1. Datasets 1k / 10k / 100k

|---|---|---|---|
| 1k records | 25 ms / 76 ms | 218 ms / 442 ms | PASS |
| 10k records | 251 ms / 350 ms | 1,924 ms / **7,760 ms** | **FAIL** (finish p95) |

- **Causes (architectural, correctness-first by design):**
  1. `begin()` snapshots **all** active records into `snapshot_json`
     (O(n) per run).
  2. `recall()` loads the whole `memories` table and filters in Python
     (O(n) per query).
- **Follow-up (not done):** snapshot only the read set; indexed recall.
- **What was NOT done to pass:** thresholds were not lowered and
  datasets were not shrunk. The gate stays FAIL until a re-run on the
  same manifest passes.
- **Practical consequence:** at 1k records the product is interactive;
  at 10k a finish takes seconds; at 100k a recall takes ~3 s. Do not
  use this release for large scopes expecting interactive latency.

## 5. External-action atomicity — NOT_SUPPORTED

- A finish receipt proves only that the local SQLite database accepted
  the commit (`guarantee: "local_sqlite_commit_only"`). It does not
  make an email, a deployment, a payment or any other external action
  atomic, and it does not prove the external world changed.
- The product never claims otherwise; any UI/docs wording that implies
  external atomicity is a bug, not a feature.

## 7. Single trusted OS user — no multi-tenancy, no auth boundary

- Scope is a correctness boundary (which project's records a run may
  see), not a security boundary against another local user who can
  read the database file. The workbench token protects a loopback HTTP
  server on one machine; it is not user authentication.
- Actor is a label bound at server/CLI start; a request body cannot
  rebind it, but anyone who can run the CLI against the DB file can
  act as any actor.
- Do not run Turnkeep as a shared service for untrusted users.

## 8. Erasure has residuals — by design, and reported

- `erase` scrubs the live DB (tombstone, WAL checkpoint + VACUUM,
  verified by scanning every text column) but cannot delete backups,
  exports, old DB copies, or another client's copy of a record it
  already read. `turnkeep residuals` lists them; it never claims they
  are deleted.
- Restoring a backup taken **before** an erasure resurrects the erased
  payload — expected point-in-time behaviour, not a bug.
- If the payload is also in the append-only `events` table, erasure
  returns `PARTIAL` and leaves the record untouched — history is never
  rewritten. See `docs/retention.md`.
- **Residual reporting (2026-11-10 rework, P0-3):** `residual_report()`
  now reports `CONTROLLED_NOT_CLEAN` when a controlled table still holds
  a payload (previously it hardcoded `live_tables_clean=true` without
  scanning). The scan checks every erased record holds the tombstone
  and every receipt referencing one holds the tombstone (or no value).
- **Receipt scrub, all shapes (2026-11-11 rework, P0-R3-01):** erasure
  used to scrub only receipts shaped `{"record_id": ...}` (finish
  receipts); remember / correct / retract / resolve_conflict receipts
  store `dump_record()` output (`{"id": ..., "value": ...}`) and begin
  receipts nest record dumps inside `"records"` lists, so those copies
  survived erasure and the erase came back PARTIAL with no way to
  complete it. The scrub now recognises dumps by owner id in either
  shape, including nested dumps, and a second `erase_record()` on an
  already-erased record re-runs the scrub + scan for that record
  (repair: no resurrection, no second revision bump), so a PARTIAL
  erase left by the old scrub can still be completed. Residuals from
  receipt rows are now attributed to the owning record id / key
  (previously `None` / `None`); residuals persisted by the old code
  with no record id are attributed via the erase event's affected ids.
- **Controlled reason labels only — no free text is persisted (2026-11-11 rework, P0-R6-01):**
  erase reasons (first erase and repair) and retract reasons are now
  controlled labels only — free text is never accepted, because no
  verbatim check can be complete against it: a secret glued into a
  longer token ("rotatedabcagain") or reversibly encoded (Base64,
  percent-encoding, reversed, hex, rot13, …) contains no verbatim
  needle, so the old substring/token check passed it and the
  recoverable text landed in the append-only event log while
  `residual_report()` still said clean. First-erase labels are
  `{"cleanup", "repair", "rotation"}` — rotation: credential/secret
  rotation (the privacy-driven erase); repair: re-erase/repair of a
  prior erase; cleanup: data-hygiene deletion of records no longer
  needed. Retract labels are `{"correction", "superseded",
  "withdrawn"}` — correction: the recorded value is no longer true;
  superseded: replaced by newer information; withdrawn: the statement
  is withdrawn. A reason outside the allowlist is rejected
  (`INVALID_INPUT`, naming the allowed labels) and nothing is
  published; only the label is persisted in the event's metadata.
  The label is still vetted against the payload needles as a second
  layer (token/substring, plus stored-hash vetting for repair), so a
  label that IS the erased value (a payload literally `"repair"`,
  erased with reason `"repair"`) is rejected too. `set_expiry`'s
  `valid_until` is instead validated as an ISO-8601 timestamp with a
  timezone (the format `_now()` produces) — a non-timestamp is
  `INVALID_INPUT`, and an encoded secret cannot be a timestamp; the
  same validation applies on `import_package`. The same
  verbatim-`reason` pattern was audited across every `publish_event`
  metadata site: all other sites carry only ids, keys, hashes or
  counts (remember / correct / resolve_conflict / finish / import /
  rebase / expire_sweep), except the frozen T004 reference core
  (`store.py`), whose events intentionally store full before/after
  record dumps by design — it has no erasure operation and is out of
  scope for this guard. The `replacements` rows written by
  correct / resolve_conflict / import / `insert_record` carry only the
  fixed literals `"correct"`, `"resolve_conflict"`, `"import"`,
  `"replacement"` — never caller text.
- **Already-leaked reasons cannot be scrubbed (append-only):** a reason
  that carried a payload into the `events` table before this fix is
  there permanently — history is never rewritten, `residual_report()`
  does not scan events, and no erase can remove it. The fix only
  prevents new leaks. To recover a leaked database: export the scope,
  import the package into a fresh database, and delete the old database
  AND the export package — import records ONE import event and does not
  replay raw events, so the fresh database is clean, but the export
  package's `events.jsonl` still contains the leaked reason.
- **Needle check is now only a second layer behind the allowlist (2026-11-11 rework, P0-R6-01):**
  the token/substring needle check (P0-R4-01: a needle appearing as a
  standalone token is refused whatever its length; a ≥ 4-character
  needle appearing as a substring is refused) survives only to vet the
  surviving label — it catches a label that is itself the erased
  value. It is not a completeness claim: an encoding contains no
  verbatim needle, so no matching over the reason can catch it; only
  the allowlist closes that class, by never persisting free text. The
  old "x" in "box" false-positive guard no longer applies to reasons
  (there are no free-text reasons anymore); the corresponding guard
  now is that a clean label erase still succeeds for a 1-character
  payload. Prevention only: a leak already in an existing DB cannot
  be scrubbed (append-only; remedy above) — and note the remedy's
  import step now rejects a package whose `valid_until` is not an
  ISO-8601 timestamp, so a pre-fix leaked `valid_until` must be
  stripped or repaired to a real timestamp in the package before
  re-importing it.
- **Repair erase accepts only controlled reason labels (2026-11-11 rework, P0-R5-01):**
  a repair erase (second erase of an already-erased record) accepts NO
  free text: its reason must be one of the controlled labels `{"repair",
  "rotation"}` and the label is hash-checked against the HMACs the first
  erase persisted in its event (and, for pre-fix erasures, against their
  raw SHA-256 hashes) — so a label that is itself the erased value (a
  payload literally `"repair"`, repaired with reason `"repair"`) is
  rejected, and only the label is persisted in the repair event's
  metadata (`"reason"`), never caller-supplied text. Guarantee: no free
  text is ever persisted by a repair erase, so no glued secret can enter
  events through it, whatever its shape (`"rotation:<secret>"`,
  `"x<secret>y"`, `"?api_key=<secret>"`). This closes the residual risk
  the P0-R4-02 token vetting documented (a secret glued into surrounding
  text with no token boundary produced no matching token and slipped
  through); the token/hash vetting survives only as a second layer
  behind the allowlist. The first-erase and retract paths take the same
  shape now (P0-R6-01): first erase accepts only `{"cleanup", "repair",
  "rotation"}`, retract only `{"correction", "superseded", "withdrawn"}`,
  each vetted against the live needles as a second layer; `set_expiry`
  validates `valid_until` as ISO-8601 instead. A repair
  erase with a reason outside the allowlist is rejected (`INVALID_INPUT`,
  naming the allowed labels) and publishes nothing. Pre-fix repair
  events that already leaked a reason into an existing DB cannot be
  scrubbed (append-only; remedy above).
- **Payload scan is scope-filtered (2026-11-11 rework, P2-R5-02):**
  `_scan_payload` and `_describe_remaining`'s rowid resolution now
  filter by `scope_id`, so one scope's erase never sees another scope's
  rows. Previously the scan was unscoped: erasing a record in s1 while
  a second live record in s2 held the same secret returned PARTIAL, and
  the persisted `remaining` entry named s2's record id and key
  (cross-scope disclosure). A same-secret record in another scope is now
  neither a residual nor named in the erase outcome, and a secret
  present only in another scope's append-only events no longer refuses
  this scope's erase. A second live record sharing the payload *in the
  same scope* is still reported PARTIAL, as before.
- **Needle hashes are HMACs, not raw SHA-256 (2026-11-11 rework, P0-R4-04):**
  erase events used to carry raw SHA-256 of every needle, so a 4-digit
  PIN was recoverable by enumerating 0000–9999 against an exported
  `events.jsonl` alone. Hashes are now HMAC-SHA256 keyed by a per-scope
  secret stored in the `scope_secrets` table (live DB only, never
  exported — export copies events + records only). Events carry no
  recoverable material, same as receipts. Cost: pre-fix events already
  written (and exports already made from them) still carry raw hashes
  and stay enumerable — the fix protects new exports; it cannot
  un-share old ones.
- **LIKE wildcards + structural text (2026-11-11 rework, P1-R4-06):**
  `_scan_payload` escapes `\`, `%`, `_` and uses an explicit `ESCAPE`
  clause, so payloads of "%" or "_" erase COMPLETE instead of being
  refused as if they matched every text cell. The scan also covers only
  payload-bearing columns now (`value_json`, receipts, task labels,
  event metadata — see `erasure._PAYLOAD_COLUMNS`): enum / identifier
  columns can never hold a payload copy, and scanning them turned
  structural text into phantom residuals (every `source_type` contains
  '_', every `event_type` contains 'e'). The erased record's own
  tombstone row is excluded from the post-scrub scan while it holds
  exactly the tombstone — the marker `{"_erased": true}` itself contains
  '_' and "true", so a needle that is a substring of the marker would
  otherwise match the tombstone. A future migration adding a
  payload-bearing table/column must register it in `_PAYLOAD_COLUMNS`.
- **1-character payloads colliding with structural key names (honest limit, split in two by the R11 rework — see §24):**
  the scan is text-based, so a 1-character payload that appears in a
  structural JSON key name still reports PARTIAL — e.g. value "e" is
  refused because every event's metadata contains the key name "key".
  That is fail-closed (the record stays active, nothing is claimed
  deleted), but the export-to-fresh-DB remedy does not help here either:
  the fresh DB's events carry the same key names. R7 rework (P0-R7-01c):
  the scan became value-aware for TIMESTAMP values — a needle occurrence
  inside a legal timestamp held under a timestamp field name (an
  expire_set event's valid_until, a receipt dump's created_at /
  updated_at / valid_until) is no longer a hit, so short values such as
  "202" / "2026" erase COMPLETE. R8 rework (P0-R8-02, P2-R8-03): the
  scan is now fully structure-aware — it knows each cell's (table,
  column) and each string's position inside it, so the timestamp
  exemption applies only at real audit positions (never inside user
  data, whatever its field name), and an identifier field counts only
  on whole-value equality (a random id merely containing a short needle
  substring is not a copy). R11 rework (P2-R11-03, see §24) splits the
  key-name rule in two: AUDIT-structure dict key names are no longer
  substring-matched (they are fixed schema words — a payload cannot be
  written through a key name, so "e" in an event's "key" field name no
  longer refuses the erase), while USER-DATA key names — the "value"
  subtree of a record, where a user string can be a key — are still
  matched raw, so a 1-char payload colliding with a user-data key name
  (e.g. value "e" against another record's `{"key": "note"}`) still
  reports PARTIAL, fail-closed. The two are documented separately:
  the audit-structure fix in §24, the user-data honest limit here.
- **Run task text can hold an encoding of an erased payload (accepted limitation, P0-R6-01 adjacent):**
  `runs.task` is operator working text, stored in a payload-bearing
  column and covered by the post-scrub scan. A verbatim needle in a
  task already makes a later erase PARTIAL (the scan covers
  `runs.task`) — and since the R11 rework (see §24) the residual
  report flags it (`task_text` + `task_locations`, e.g. `"runs.task"`)
  and a repair erase carries it forward (still PARTIAL), so the report
  can never be misled into clean while the task still holds the
  payload. A reversible encoding of the payload in a task is NOT
  scanned for — no complete code fix exists for it (any fixed decoder
  set is incomplete by construction, same as for reasons; the task has
  no erase target at write time). After erasure the encoding can
  remain in `runs.task` while `residual_report()` says clean. Do not
  paste secrets, or encodings of them, into run task text.

## 9. Retrieval is lexical, not semantic

- Recall is scope-first filtering + FTS/lexical ranking (with a
  Chinese token fallback). There is no embedding, no vector search,
  no semantic similarity merge. Same-key conflicts are explicit;
  same-meaning-different-key conflicts are **not** detected. Do not
  describe recall as understanding meaning.
- Budgets count **characters** (and an estimated token count labelled
  as an estimate), never `len()` passed off as exact tokens.
